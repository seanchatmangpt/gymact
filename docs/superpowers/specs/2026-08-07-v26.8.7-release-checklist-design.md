# GymAct release checklist: landing today's work and cutting the next real release

## Context

`pyproject.toml` and `CHANGELOG.md` both already say `26.8.7`, but no git tag
(local or remote) has ever been created for it — PR #2 ("feat: release
GymAct v26.8.7") set the version string without the release pipeline ever
actually firing. Since then, substantial new work has accumulated:

- `CHANGELOG.md`'s `[Unreleased]` section already lists 6 real, shipped
  features (OCEL 2.0 export, `probe_repo`, `GenericDiscoveredProvider`,
  `discover_and_actuate.py`, `ocel_standing.py`, wasm4pm cross-validation).
- 4 more real gym providers exist in the working tree right now, fully
  implemented and tested but **entirely uncommitted**:
  `kubernetes_reconciliation.py`, `mcp_client_session.py`,
  `terraform_docker_apply.py`, `terraform_plan.py`, plus their test files
  and new fixtures.
- One tracked file is modified but not yet committed:
  `tests/fixtures/real_episode.ocel.json`.
- `.claude/worktrees/` is untracked and should not become part of any
  commit.

The repo's actual release mechanism (`.github/workflows/release.yml`) is
commitizen-driven: pushing a commit whose message starts with `bump:` to
`main` triggers an automated tag + GitHub release + PyPI trusted-publish
(OIDC, no manual token — relevant since this session has no PyPI key,
established earlier). No manual tagging or manual `pypi` upload is part of
the intended workflow, and none should be improvised here.

Scope decisions made during brainstorming:
- Today's 4 uncommitted providers **are** in scope for this release.
- The concurrent open draft PR #4 ("Wire real BrowserGym openended gym")
  is **explicitly out of scope** — ship without it; it lands in a later
  version whenever it's actually ready.
- The next version number is **not assumed to be `26.8.7` again** — that
  string was already spent once without a tag. `cz bump` computes the real
  next version from the conventional-commit types of what's actually
  landing.

## Design

### 1. Pre-flight verification (before anything is committed)

Gate on real, current evidence, not memory of an earlier run:

- Full test suite green: `GYMACT_ALLOW_DEGRADED_STANDINGS='LOCAL_GYM:kubernetes-reconciliation'` (or the broader `'*'` if terraform/docker are also transiently unavailable in the release environment) `.venv/bin/python -m pytest tests/ -v` — every named skip must have a real, current reason, not a stale one.
- `grep -rnE "unittest\.mock|Mock\(|MagicMock|patch\(|monkeypatch|@patch|create_autospec|mocker\." --include="*.py" src/ tests/ scripts/` → zero matches, matching this session's discipline throughout.
- `CHANGELOG.md`'s `[Unreleased]` section is read end-to-end and corrected if it overclaims — it should describe exactly the 4 new providers plus the 6 already-listed items, nothing aspirational (e.g. no claim that `ocel_standing.py`'s standing model generalizes beyond the `discovered` family — it doesn't yet, per this session's own finding).

### 2. Landing today's uncommitted work

- Confirm `.claude/worktrees/` is either already `.gitignore`d or gets added there — it must never enter a commit.
- Stage and commit the 4 new providers + their tests + new fixtures using real conventional-commit messages (`feat: ...`) so commitizen's version-bump computation is accurate, not `git commit -m "wip"`.
- Handle `tests/fixtures/real_episode.ocel.json`'s modification deliberately: diff it, confirm the change is intentional and correct (not a stray artifact from a test run), and either commit it with the relevant feature commit or revert it if it turns out to be incidental.
- Re-run the full pre-flight suite (section 1) against the now-landed tree before proceeding — landing is not verification.

### 3. Version bump and release trigger

- From clean, landed history on `main`: run `cz bump` (or `cz bump --dry-run` first to preview) and let commitizen compute the real next version from the conventional-commit types actually present since the last real tag (there is none yet, so this is effectively commitizen's first real cut).
- Review the generated `CHANGELOG.md` diff and the version-bump commit message before pushing — this is the last human checkpoint before automation takes over.
- Push the `bump:` commit to `main`. `release.yml` picks it up automatically: creates the git tag, creates the GitHub release (via `gh release create` using the changelog slice), and (in the `pypi_publish` job) publishes to PyPI via OIDC trusted publishing.

### 4. Post-release verification and rollback posture

- `gh release view <tag>` — confirm the real GitHub release exists with the expected notes.
- Confirm the real PyPI page is live at the new version (fetch `https://pypi.org/project/gymact/<version>/` or equivalent).
- Confirm the pushed git tag matches what CI actually tagged (`git ls-remote --tags origin`).
- One real smoke test: `pip install gymact==<version>` into a scratch venv, confirm real import succeeds.
- **Rollback posture, stated explicitly rather than assumed**: a bad git tag/GitHub release is cheap to delete and redo. A bad PyPI publish is **not** — PyPI does not allow re-uploading the same version number even after deletion. This makes section 1's pre-flight gate the actual safety mechanism, not any post-hoc rollback; if pre-flight is skipped or wrong, there is no clean undo once `pypi_publish` succeeds.

## Verification (end-to-end, for the checklist itself)

```
cd ~/gymact
GYMACT_ALLOW_DEGRADED_STANDINGS='*' .venv/bin/python -m pytest tests/ -v
grep -rnE "unittest\.mock|Mock\(|MagicMock|patch\(|monkeypatch|@patch|create_autospec|mocker\." --include="*.py" src/ tests/ scripts/
git add <landed files>   # explicit paths, never `git add -A` given untracked worktree dirs present
git commit -m "feat: ..."  # one real conventional-commit message per logical addition
cz bump --dry-run   # review computed version before committing to it
cz bump
git push origin main
# then, after CI completes:
gh release view <tag>
git ls-remote --tags origin
pip install gymact==<version> --target /tmp/gymact-smoke-check && python -c "import gymact"
```

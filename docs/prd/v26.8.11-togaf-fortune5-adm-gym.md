# PRD/ARD — GymAct v26.8.11: Fortune-5 TOGAF ADM Simulation Gym

Status: M1 vertical slice implemented and superseded; the generalized ontology-driven compiler
described below is implemented and verified. Target version: 26.8.11.

## Architecture correction (post-M1)

The first implementation pass (M1) hand-coded two ADM phases as Python `if`/capability branches
directly in `togaf.py`. That was rejected as the wrong abstraction: GymAct should not become "a
growing collection of manually implemented benchmark adapters." TOGAF is a forcing function/case
study for the architecture, not the architecture itself. The corrected, implemented design:

- A new, domain-agnostic module, `src/gymact/gyms/ontology_gym.py`
  (`OntologyDrivenProvider`/`OntologyDrivenEnvironment`), mechanically compiles a real, executable
  `EnvironmentProvider` directly from any pack's `pplan:Plan`-shaped `ontology.ttl` — precondition
  chain, multi-subject task expansion, and effects are all derived from the graph, not hand-coded.
- `togaf.py` shrank from a ~190-line hand-coded environment to a ~40-line configuration
  (`build_togaf_provider()`) over that generic compiler — `ggen/togaf-gym-pack/ontology.ttl`'s
  ten existing `pplan:Plan` tasks were consumed **unmodified**; no ontology changes were needed to
  unlock full 10-phase coverage.
- Authority tiering (standard vs. Architecture-Board/governance) and the Phase H → Requirements
  Management loop-back are both expressed as caller-supplied family-name configuration
  (`elevated_task_families`, `reset_task_families`/`reset_target_families`) consumed by a new
  `TieredAuthorityResolver`, not TOGAF-specific Python.
- Verified live: all 10 ADM phases, real precondition chain, real governance-authority separation,
  a real Phase H reset that clears Requirements Management's facts and a real recovery that
  re-establishes them — `reports/ocel/togaf/episode.ocel.json` independently re-derived as
  `GYMACT_ACTUATED` (schema-valid, conformant replay, real `solved=True` on an act event).
- `tests/test_ontology_gym.py` proves the compiler itself is domain-agnostic against a synthetic,
  non-TOGAF fixture; `tests/test_togaf_gym.py` proves the *generated* TOGAF provider satisfies the
  same kernel contract.

Still explicitly out of scope, unchanged from the original PRD: `pyshacl`-backed per-task
verification (the kernel's default `DictSubsetVerifier` remains the judge), real `odrl:Permission`
RDF instances (the two-tier authority-family sets are the working mechanism-equivalent),
synthetic Fortune-5-scale multi-enterprise instantiation, and generalizing the compiler's input
contract beyond `pplan:Plan`-shaped packs to other domains (Kubernetes/AWS/etc.).

## Context

This document specifies what GymAct needs so the entire TOGAF Architecture Development Method
(ADM) lifecycle can be simulated end-to-end, actuated by either an autonomous agent or a human,
through GymAct's real kernel (`materialize`/`observe`/`act`/`verify`), with the same authority,
verification, and evidence guarantees every other gym in this repo already has.

**Grounding finding that shapes this whole document**: `ggen/togaf-gym-pack` is real and
well-formed — a public-ontology ABox (PROF/PROV-O/ORG/SKOS/OSLC-RM/DCAT/ODRL), ten `pplan:Plan`
task definitions (one per ADM phase, `togaf.00.preliminary` through `togaf.80.phase-h`), three
SPARQL gates, and a Rust/WIT reference-doc projection — but **there is no Python
`Environment`/`EnvironmentProvider` for TOGAF at all** (confirmed: `src/gymact/gyms/` has no
`togaf.py`; the ontology declares zero `sosa:Procedure` capability facts). Today, `togaf-gym-pack`
cannot be materialized, observed, actuated, or verified through the real kernel — it is a semantic
profile and a documentation projection, not an actuatable gym. "Simulate the entire process with
agents or humans" is not possible with the current codebase. That gap is this PRD's subject.

## Non-goals (explicit, load-bearing)

- **GymAct does not reason, plan, or decide which candidate architecture is best.** Per
  `.claude/rules/explore-exploit.md`, that belongs in a lab repository (e.g. `autofde-lab`) — the
  `SELECT`/`CONSTRUCT` half of the gym algebra, owned by callers, not GymAct
  (`docs/2026-08-08-gymact-constitution.md`). This PRD scopes GymAct to `OBSERVE`/`DO`/`VERIFY`
  only: hold the world (the enterprise architecture repository state), gate actuation (authority),
  and independently verify phase-exit criteria. An agent or human proposes; GymAct never proposes.
- **GymAct does not reproduce TOGAF's copyrighted standard text, diagrams, or templates.** Same
  fence `togaf-gym-pack/README.md` already states: public source identifiers and short public
  phase labels only, plus independently-authored synthetic enterprise data.
- **GymAct does not replace real enterprise-architecture tooling.** It is a bounded, verifiable
  simulation surface for training/benchmarking agents and evaluating process conformance — the
  same role every other gym in this repo plays for its domain.
- **No new public ontology terms.** The existing `togaf-gym-pack/ontology.ttl` stack is sufficient;
  this PRD adds Python actuation and ABox instances, never new TBox, per
  `.claude/rules/ontology.md`.

## Users (both go through the identical authority/verification path)

- **Human EA practitioner** — via CLI/MCP surface (`gymact.surfaces.cli`/`gymact.surfaces.mcp`,
  thin compositions per `.claude/rules/python-native.md`).
- **Autonomous agent** — via the same MCP surface, or directly via `GymAct`/`ProductionGymAct`
  (the same `authority_ref`/`principal` mechanism `gymact.discovery.DiscoveryProbeRunner` already
  uses for LLM-driven actuation).

Because both actors cross the same `_authority_decision()` gate and the same independently-injected
`PostconditionVerifier`, results from a human-run and an agent-run ADM simulation are directly
comparable — that comparability is the acceptance bar for "simulate with agents or humans."

## Architecture

### 1. State model `S` — the enterprise architecture repository

A real Python model (Pydantic, per `.claude/rules/python-native.md`) representing the artifacts an
ADM engagement produces and consumes, grounded in the existing ontology stack (instances of
`prov:Entity`, `org:*`, `oslc_rm:Requirement`, `dcat:Resource` — no new classes):

- Stakeholders, principles, drivers, goals (Preliminary/Requirements Management).
- Requirements with traceability links (OSLC RM, already used in `togaf-gym-pack`).
- Per-phase architecture artifacts (Vision, Business/Data/Application/Technology target
  architectures, Options portfolio, Migration roadmap, Governance/Conformance record, Change
  record) — one artifact type per existing `dct:subject` already declared in `ontology.ttl`'s ten
  task definitions.
- Governance decisions (Architecture Board approvals) as `odrl:Permission` instances.

### 2. Capabilities `C` — one `sosa:Procedure` per real ADM action, split READ/DO

Extending `ontology.ttl` (not replacing it) with real capability facts the ten existing
`pplan:Plan` tasks currently lack:

| Phase | READ capability | DO capability |
|---|---|---|
| Preliminary | `inspect_capability_baseline` | `establish_architecture_capability` |
| Requirements Mgmt | `inspect_requirements_traceability` | `submit_requirement`, `close_requirement_gap` |
| A (Vision) | `inspect_vision` | `submit_architecture_vision` |
| B (Business) | `inspect_business_architecture` | `submit_business_architecture` |
| C (Data/App) | `inspect_information_systems_architecture` | `submit_data_architecture`, `submit_application_architecture` |
| D (Technology) | `inspect_technology_architecture` | `submit_technology_architecture` |
| E (Opportunities) | `inspect_solution_options` | `submit_solution_options` |
| F (Migration) | `inspect_migration_plan` | `submit_migration_roadmap` |
| G (Governance) | `inspect_conformance_record` | `request_governance_approval`, `record_governance_decision` |
| H (Change) | `inspect_change_backlog` | `raise_change_request` |

Every DO capability requires authority (`requires_authority=True` default, per the already-closed
8-provider gap documented in `.claude/rules/actuation-authority.md` — this gym follows the same
fail-closed default from day one, not as a later fix).

### 3. Authority boundary — governance gates as real `odrl:Permission` checks

TOGAF's own Architecture Board sign-off becomes a real, mechanically-enforced authority check:
`request_governance_approval` at Phase G is the one DO capability whose admission an injected
`AuthorityResolver` must explicitly grant before any later-phase capability (`raise_change_request`,
a Phase H action) becomes reachable — modeled as an ODRL policy scoped to the engagement's episode,
not a special-cased `if phase == "G"` in Python. This reuses `AuthorityResolver`/`CapabilityScope`
exactly as they exist today; no kernel changes.

### 4. Verification — SHACL shapes as the real `PostconditionVerifier`, per phase

`rust/togaf_gym/shapes.ttl` (SHACL courts, already real, already used by
`test_ggen_togaf_gym_pack.py` for gate-time validation) becomes the actual per-phase exit-criteria
verifier at runtime, via a `pyshacl`-backed `PostconditionVerifier` implementation (same injection
point `gymact.verification.PostconditionVerifier` already defines — no kernel change, a new
implementation). A phase is not "done" because an agent claims it is; it's done because the
repository state, independently re-observed, satisfies that phase's SHACL shape.

### 5. Full-lifecycle composition and evidence

The ten existing `pplan:Plan` task definitions become the real sequence a simulated engagement
walks. GymAct does not decide the path (that's the caller/`autofde-lab`'s job per the SELECT/
CONSTRUCT boundary) — it executes each phase's DO/VERIFY pair and emits one continuous OCEL 2.0
log per engagement (`gymact.ocel`, unchanged), so the whole ADM run — not just one phase — is
independently, schema-valid, conformant-replayable, matching `.claude/rules/ocel-standing.md`'s
existing bar. Concretely: a real `reports/ocel/togaf/episode.ocel.json` with ten phase-transition
event clusters and one final `solved=True` evidence marker for full-cycle completion.

### 6. Synthetic Fortune-5-scale data

A generator producing independently-authored synthetic enterprise scenarios at realistic scale
(multiple business units, application portfolios spanning legacy/cloud, multi-region technology
estates) — extending, not replacing, `togaf-gym-pack`'s existing "independently authored synthetic
enterprise data" fence. Never TOGAF's own text/diagrams; never a real company's actual data.

## Files (implementation surface)

- `src/gymact/gyms/togaf.py` — `TogafEnvironment`/`TogafProvider`, following the same shape as
  `src/gymact/gyms/opaque_procedure.py`/`kubernetes_reconciliation.py` (real `materialize`/
  `observe`/`actuate`/`verify`/`checkpoint`/`restore`/`teardown`).
- `src/gymact/verification.py` — add a `ShaclPostconditionVerifier` (or similar) alongside the
  existing `DictSubsetVerifier`, backed by `pyshacl` against `rust/togaf_gym/shapes.ttl`.
- `ggen/togaf-gym-pack/ontology.ttl` — extend with the READ/DO `sosa:Procedure` capability facts
  above (additive; the ten existing `pplan:Plan` tasks are unchanged).
- `tests/test_togaf_gym.py` — real, Chicago-style: a real `TogafEnvironment`, real SHACL
  verification, real authority-gated Phase G transition, no mocks.
- `tests/test_ocel_standing.py` — add the `togaf` subject once a real
  `reports/ocel/togaf/episode.ocel.json` exists (this repo's own required pattern — no hardcoded
  expected value, direct log/replay assertion).

## Milestones toward v26.8.11

- **M1 — vertical slice**: Preliminary + Requirements Management only. Real environment, real
  authority gate on `submit_requirement`, real OCEL evidence for a 2-phase episode. Smallest
  possible real, end-to-end, non-simulated proof the pattern works before building out all ten.
- **M2 — Phases A–D**: artifact submission + SHACL verification per phase (Vision through
  Technology Architecture). No governance gating yet — those phases don't require it in TOGAF's
  own structure.
- **M3 — Phases E–H**: authority-gated Governance Board approval at Phase G, full ten-phase OCEL
  replay test, `solved=True` full-cycle marker.
- **M4 — scale + parity**: synthetic Fortune-5-scale data generator; a real test proving a human-
  actuated run and an agent-actuated run produce independently-verifiable, structurally comparable
  OCEL logs (the "agents or humans" acceptance bar). Decide explicitly whether this gym runs in
  CI's `core` matrix (like `kubernetes-reconciliation`/`terraform-docker-apply`, which run for real
  in CI today) or stays `LOCAL_GYM`-degraded — a real decision to make at M4, not assumed here.

## Acceptance criteria (binding, per this repo's own standard)

Per `.claude/rules/ocel-standing.md`: this gym's "works" claim is never a pytest verdict. Done
means a real `reports/ocel/togaf/episode.ocel.json` exists, passes `validate_ocel_log` against the
OCEL 2.0 schema, replays conformant via `ConformanceChecker`, and carries a real `solved=True` act
event for full ten-phase completion — asserted directly in a test reading that log, not via a
hardcoded string or a summarizing script's own verdict.

## Explicitly out of scope for v26.8.11

- Any planner/hypothesis-portfolio logic for choosing between candidate architectures — belongs in
  `autofde-lab` if pursued.
- CI wiring beyond the M4 decision point above.
- A generalized "any enterprise framework" abstraction — this PRD is TOGAF-specific, matching how
  every other gym in this repo (`kubernetes_reconciliation.py`, `terraform_docker_apply.py`) is
  domain-specific rather than a generic framework.
